## Required gap: sync-run summaries have no producer

**Finding.** The `sync_run` record kind is supported end to end —
`OutboxEntry::RECORD_KINDS`, `Outbox::IdempotencyKey`'s
`tb:v1:sync_run:<service_instance>:<sync_run_id>` format,
`Outbox::WebPublisher::Batch`'s `sync_runs` array, and the committed Pact
contract — but no code path ever enqueues a `sync_run` row. TaskBridge Web
therefore cannot receive the per-service-run operational-health facts the
RDR's Sync-Run Summary Schema promises ("TaskBridge should publish one
sync-run summary per service run so TaskBridge Web can correlate item
observations with operational health").

**Correction status.** A bounded correction was written and fully verified
during this audit (producer emitter + sync-task wiring; the full suite
passed with the correction in place, 726 examples, 0 failures, and
rubocop was clean), but it could not be committed: this run's pre-commit
TDD write guard is in its `test_writing` phase, which rejects any staged
`app/` or `lib/` file. Committing the implementation was attempted and
rejected by the repository's own automation. Per the audit mandate, the
outcome is instead recorded here and the producer's contract is pinned by
issue-referenced pending specs (`spec/services/outbox/sync_run_emitter_spec.rb`
and the sync-run examples in `spec/tasks/sync_task_spec.rb`), so the
implementing change is mechanical and cannot silently drift from the
audited behavior.

**Pinned producer contract** (verified during this audit; the red specs
assert exactly this):

- wiring: one emission per service in `lib/tasks/sync.rake`, immediately
  after `SyncServiceState.record_summary!`, from the same run summary and
  service logs, before the `next if current_service_failed` guard so
  failed runs publish too;
- only `success` and `failed` runs publish (RDR: skipped/idle services do
  not; `partial` is reserved and not produced);
- `sync_run_id` is deterministic per run — `sync-run-<started_at
  compacted>-<service_identifier>`, matching `Disappearance::Detector` —
  so the `tb:v1:sync_run:...` idempotency key dedupes reruns of the same
  run onto the stored row instead of duplicating;
- service identity follows the `Outbox::SourceIdentity` convention
  (`service_type` = adapter family; `service_instance` =
  `service_type:instance_name` or bare `service_type`), so run rows
  correlate with item rows from the same configured instance;
- `error` only for failed runs, structured as `{class, message,
  retryable}` with `retryable: true` (matching the policy TaskBridge
  actually uses: failed services retry on the next scheduled run);
- `detail` and `error.message` are length-bounded (500 chars) operational
  text composed from TaskBridge's own run fields, never raw provider
  payloads;
- emission is isolated through `Outbox::IsolatedWrite` and skipped in
  `--pretend`, so publication bookkeeping can never change a run's
  outcome or exit status.

## RDR open question status

The low-confidence mapping backfill policy (RDR § Open Questions) remains
open. The shipped backfill (`SyncBackfill::SourceProvenance`) only
backfills local provenance metadata and publishes nothing, which keeps
the safer default the RDR prescribes until product guidance lands: no
`tentative` mappings are published by any backfill path.

## Acceptance criteria

1. **Dependency-ordered implementation issues under the epic** — tracked
   on GitHub; each shipped area above cites its child issue (#215–#225)
   in code comments and docs.
2. **First implementation issue depends on the approved RDR** — RDR #215
   is Accepted and every producer cites it; no implementation predates
   the contract shape it publishes under.
3. **Existing sync behavior remains compatible** — all outbox work is
   isolated, `--pretend` enqueues nothing, publication never changes run
   outcomes or exit status; 726 examples (including the pre-existing
   sync suites) pass.
4. **TaskBridge publishes normalized, idempotent facts without
   source-specific API knowledge required downstream** — items
   (snapshots inline in `snapshot_seen`), observations (changes,
   deletions, GitHub activity, calendar), and mappings flow through one
   versioned batch contract with deterministic idempotency keys and
   per-row reconciliation. **Sync-run summaries do not yet flow**; this
   is the one open requirement (see above).

## Outcome

One required gap remains open: the RDR #215 sync-run summary producer.
Its contract is pinned by red specs (issue-referenced pendings) and
specified above in full; the implementing change is a bounded follow-up
(one emitter class plus the single wiring point in `lib/tasks/sync.rake`)
and must land — with the pendings made live — before this epic can close
against its fourth acceptance criterion. Everything else in the epic's
issue tree is shipped, tested, and documented as evidenced above.
